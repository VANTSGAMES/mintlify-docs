[`flask-agents`](https://github.com/vantsgames/flask-agents) contiene tres aplicaciones independientes: una web Flask de soporte, un servicio Node.js de vigilancia y acciones, y un consumidor Python del bus de eventos. Esta guia describe cada componente, sus contratos de entrada/salida, variables de entorno, limites y relaciones verificadas con otros repos del ecosistema.

Revision: 1 de noviembre de 2026. Commit: `3282d92` (HEAD actual, identico a la revision previa).

## Web Flask (soporte)

### Arranque local

```bash
git clone https://github.com/vantsgames/flask-agents.git
cd flask-agents
python3 -m venv .venv
source .venv/bin/activate
python -m pip install -r requirements.txt
python main.py
```

La app escucha en `0.0.0.0:8000` con `debug=True`. Solo para desarrollo protegido.

### Endpoints de la web

| Metodo y ruta | Funcion | Cuerpo de entrada | Respuesta (exito) | Errores conocidos |
| --- | --- | --- | --- | --- |
| `GET /healthz` | Estado del proceso Flask | - | `{"ok": true, "servicio": "web-agentes-vants"}` | - |
| `GET /api/agentes` | Catalogo del squad | - | `{"ok": true, "agentes": [...], "total": 4}` | - |
| `GET /api/ia` | Estado de la capa IA | - | `{"ok": true, "activo": bool, "modelo": "...", "proveedor": "...", "fallback": "modo reglas (NLU local en espanol)"}` | - |
| `POST /api/chat` | Respuesta de soporte | `{"mensaje": string, "historial": [{"rol": "user", "texto": "..."}]}` | `{"ok": true, "modo": "llm" or "reglas", "modelo": "..." or null, "respuesta": string}` | 400 si `mensaje` vacio o > 2000 caracteres; historial recortado a 10 turnos |
| `GET /vants/bus` | Estado del consumidor del bus | - | `{"ok": true, "activo": bool, "consumidor": {...}}` | - |

### Chat de soporte: dos modos

- **Modo LLM**: activo solo con `AGENT_LLM_KEY`. Usa `AGENT_LLM_URL` (por defecto `https://api.z.ai/api/paas/v4`) y `AGENT_LLM_MODEL` (por defecto `glm-4.5-flash`). Temperatura 0.6, max_tokens 700, timeout 25 s. El prompt de sistema define la identidad "Vants Soporte" en espanol.
- **Modo reglas**: NLU local en `soporte/reglas.py`. 0 dependencias, siempre disponible. Responde sobre el squad, estado, despliegue, ORION, GLM y saludos. No inventa datos.

Si el proveedor LLM falla, el chat cae automaticamente al modo reglas sin devolver 500.

### Consumidor VANTS-BUS (integrado en Flask)

`main.py` intenta importar `vants_bus.consumer.iniciar` dentro de un `try/except`. Solo arranca si existen `VANTS_BUS_URL` y `VANTS_BUS_SECRET`. En Vercel (serverless) no arranca salvo `force=True`. El endpoint `/vants/bus` expone `_VANTS_BUS_ACTIVO` y `_VANTS_BUS_ESTADO`.

### Arranque local

```bash
cd services/agent-service
npm install
npm start   # ejecuta node server.js
```

El puerto por defecto es 8082 (`PORT`). Escucha en `0.0.0.0`.

### Endpoints del servicio

| Metodo y ruta | Auth | Operacion | Cuerpo de entrada | Respuesta (exito) | Errores conocidos |
| --- | --- | --- | --- | --- | --- |
| `GET /healthz` | Publico | Estado del servicio | - | `{"ok": true, "service": "agent-service", "version": "1.0.0", "uptime": N, "memoria": "pg" or "memoria", "cerebro": "reglas+llm" or "reglas", "sandbox": "activa"}` | - |
| `GET /api/v1/estado` | Bearer si `AGENT_TOKEN` | Ultimo run + incidentes abiertos | - | `{"ok": true, "ultimo": {...}, "incidentes": [...], "cerebro": "..."}` | 401 si token incorrecto |
| `POST /api/v1/ciclo` | Bearer si `AGENT_TOKEN` | Ejecuta vigilancia completa | - | `{"ok": true, "run_id": N, "estado": "UP" or "DEGRADED" or "DOWN", "resumen": "...", "hallazgos": [...], "acciones": [...], "ia": {...}}` | 401; puede hacer peticiones externas |
| `POST /api/v1/comando` | Bearer si `AGENT_TOKEN` | Procesa orden en lenguaje natural | `{"texto": string, "creado_por": string}` | `{"ok": true, "intencion": "...", "via": "llm-herramientas" or "llm" or "reglas", "respuesta": string}` | 400 si falta `texto`; 401 |
| `GET /api/v1/incidentes` | Bearer si `AGENT_TOKEN` | Lista incidentes abiertos | - | `{"ok": true, "incidentes": [...]}` | 401 |
| `POST /api/v1/incidentes/:id/resolver` | Bearer si `AGENT_TOKEN` | Cierra incidente | `{"resolucion": string}` | `{"ok": true, "resuelto": N}` | 404 si no existe o ya cerrado; 401 |
| `GET /api/v1/memoria` | Bearer si `AGENT_TOKEN` | Busca recuerdos | `?q=texto` | `{"ok": true, "recuerdos": [...]}` | 401 |
| `POST /api/v1/memoria` | Bearer si `AGENT_TOKEN` | Guarda recuerdo | `{"clave": string, "valor": string, "tipo": string, "importancia": number}` | `{"ok": true, "id": N}` | 400 si falta `clave` o `valor`; 401 |
| `GET /api/v1/archivos` | Bearer si `AGENT_TOKEN` | Lista archivos de sandbox | `?prefijo=ruta` | `{"ok": true, "archivos": [...]}` | 401 |

### Auth Bearer

Si `AGENT_TOKEN` esta definido, todas las rutas `/api/v1/*` exigen `Authorization: Bearer <token>`. La comparacion es timing-safe (caracter por caracter, sin cortocircuito). Sin `AGENT_TOKEN` las rutas quedan abiertas y el servidor emite un aviso en consola al arrancar.

### Ciclo de vigilancia (nucleo.js)

1. Abre run en memoria (`agent_runs`).
2. Ejecuta los 7 chequeos en paralelo.
3. El cerebro evalua resultados: `UP`, `DEGRADED`, `DOWN` o `DESCONOCIDO`.
4. Inserta incidentes con `dedupe_key` (evita duplicados; reabre si estaba resuelto).
5. Ejecuta acciones automaticas seguras (guarda anti-bucle en `agent_events`).
6. Procesa comandos pendientes de `agent_comandos`.
7. Cierra run con resumen, hallazgos, acciones y estado de la capa IA.

### Chequeos (chequeos.js)

| ID | Que vigila | Severidad si fallo | Accion automatica sugerida |
| --- | --- | --- | --- |
| `web` | Worker `vants.vants.workers.dev` (HTTP 200 + contenido VANTS) | critical | `redispatch_cloudflare` |
| `worker_faceit` | `/healthz` del webhook FACEIT | error | - |
| `launcher` | Ultima release GitHub: `.exe`, `latest.yml`, coherencia de version | error | `revisar_release` |
| `workflows` | Ultimos runs de 5 workflows (cloudflare-deploy, neon-migrate, desktop-electron, faceit-xp, tests) | warn | `redispatch_cloudflare`, `redispatch_neon_migrate`, `rerun_fallidos` |
| `neon` | Colas pendientes en `web_events`, `faceit_webhook_events`, `mm_tickets`, incidentes abiertos | error | - |
| `matchmaking` | `/healthz` del servicio de matchmaking (opcional) | warn | - |
| `vercel_deploy` | Ultimo deploy de `main` en Vercel (`READY` ok, `ERROR` or `CANCELED` fallo) | error | `redeploy_vercel` |

Timeout de cada chequeo: 15 s. Clasificacion de workflows por ruta del archivo YAML, no solo por nombre.

### Acciones automaticas (acciones.js)

| Accion | Condicion | Guarda anti-bucle | Efecto secundario |
| --- | --- | --- | --- |
| `redispatch_cloudflare` | Web caida o workflow `cloudflare-deploy` fallido | 1 vez por SHA | `POST /repos/{repo}/actions/workflows/cloudflare-deploy.yml/dispatches` |
| `redispatch_neon_migrate` | Workflow `neon-migrate` fallido | 1 vez por SHA | `POST /repos/{repo}/actions/workflows/neon-migrate.yml/dispatches` |
| `rerun_fallidos` | Otro workflow fallido | 1 vez por runId | `POST /repos/{repo}/actions/runs/{runId}/rerun` |
| `redeploy_vercel` | Deploy Vercel en `ERROR` or `CANCELED` | Maximo 2 intentos por SHA | `POST /v13/deployments?teamId=...` con `deploymentId` = uid fallido |

Sin `GITHUB_TOKEN` o `VERCEL_TOKEN` las acciones quedan propuestas (no ejecutadas). Sin memoria disponible (Neon caida) la accion NO se ejecuta (fail-safe anti-bucle).

### Memoria (memoria.js)

Dos implementaciones con la misma interfaz:

- **RAM**: `crearMemoriaMemoria()`. Usada en tests y modo degradado. No persiste entre reinicios.
- **PostgreSQL**: `crearMemoriaPg(pg)`. Requiere `DATABASE_URL` con prefijo `postgres://` o `postgresql://`. SSL habilitado salvo que la URL contenga `sslmode=disable`.

Tablas y funciones (migraciones 25 y 26):

| Entidad | Tabla/Vista | Campos clave |
| --- | --- | --- |
| Runs | `agent_runs` | `id`, `fuente`, `modo`, `estado_global`, `hallazgos` (jsonb), `acciones` (jsonb), `resumen`, `error`, `started_at`, `finished_at` |
| Incidentes | `agent_events` | `id`, `dedupe_key` (UNIQUE), `kind`, `severity`, `titulo`, `detalle` (jsonb), `accion_sugerida`, `estado`, `notificado`, `resolucion`, `created_at`, `updated_at`, `resolved_at` |
| Comandos | `agent_comandos` | `id`, `texto`, `creado_por`, `estado` (pendiente/hecho/error), `respuesta`, `entregado`, `created_at`, `respondido_at` |
| Resumen | `agent_resumen` (vista) | `incidentes_abiertos`, `incidentes_graves`, `comandos_pendientes`, `web_events_pendientes`, `ultimo_estado`, `ultimo_run_en`, `ultimo_resumen` |
| Recuerdos | `agent_memoria` | `id`, `clave` (UNIQUE), `valor`, `tipo`, `importancia` (1-5), `expira_en`, `creado_por`, `created_at`, `updated_at` |

### Sandbox (sandbox.js)

Ejecuta comandos en el entorno donde ya corre (runner de GitHub Actions o maquina local). No es un sandbox aislado a nivel de sistema operativo; es una capa de validacion y auditoria.

Reglas de seguridad:

1. **Allowlist** por segmento de pipeline: `node`, `npm`, `npx`, `python3`, `pip3`, `ls`, `cat`, `head`, `tail`, `wc`, `grep`, `rg`, `find`, `echo`, `date`, `uname`, `df`, `du`, `ps`, `sleep`, `sort`, `uniq`, `cut`, `awk`, `sed -n`, `jq`.
2. **Denylist**: `rm -rf`, `sudo`, `ssh`, `scp`, `killall`, `shutdown`, `reboot`, `mkfs`, `dd`, `chmod 777`, `chown`, `curl -X POST/PUT/DELETE/PATCH`, `wget`, `gh secret/auth`, `git push`, `git reset --hard`, `npm publish`, `eval`.
3. Prohibidos: backticks, `$(...)`, `;`, `&&`, `&`, redirecciones `>`, `<`, saltos de linea.
4. Prohibido cualquier string que parezca un secreto (`ghp_`, `github_pat_`, `sk-`, `xoxb-`, `AKIA...`, `-----BEGIN`).
5. Timeout: 10 s por defecto, maximo 30 s. Salida recortada a 32 KB.
6. Todo auditado en `agent_sandbox_execs`.

Resultado de `sandbox.ejecutar(comando)`:

| Campo | Tipo | Descripcion |
| --- | --- | --- |
| `permitido` | boolean | `false` si la validacion rechazo el comando |
| `exitCode` | number or null | Codigo de salida del proceso (124 si timeout) |
| `duracionMs` | number or null | Duracion real en milisegundos |
| `timeout` | boolean | `true` si se mato por timeout |
| `texto` | string | Resumen legible con exit, duracion, salida, errores |

## Consumidor VANTS-BUS (Python)

### Dos modos de uso

1. **Integrado con Flask** (VPS/local): `main.py` arranca un hilo daemon si hay `VANTS_BUS_URL` y `VANTS_BUS_SECRET`.
2. **Proceso independiente** (recomendado; Vercel mata hilos de fondo):

```bash
VANTS_BUS_URL=https://vants-bus.vants.workers.dev \
VANTS_BUS_SECRET=<secreto> python vants_bus/consumer.py
```

### Eventos consumidos

| Tipo | Reaccion por defecto |
| --- | --- |
| `match.finished` | Publica `post.generated` con resumen del partido |
| `tournament.inscriptions_opened` | Publica `post.generated` anunciando torneo |
| `clip.highlights_ready` | Log informativo |
| `clip.published` | Log informativo |
| `alert.detected` | Log con nivel de alerta |
| `match.scheduled`, `match.canceled`, `inscription.created`, `game.session_started` | Log informativo |

### Cursor persistente

El cursor se guarda en `vants_bus/.vants-cursor.json` tras cada lote. En la primera ejecucion sin historial, empieza "desde ahora" con un ULID-like generado a partir del timestamp actual. Esto evita reproducir todo el historial del bus.

### Cliente del bus (vants_bus_client.py)

Solo biblioteca estandar: `hmac`, `hashlib`, `json`, `urllib`. Sin dependencias.

Firma: `X-VANTS-Signature = hex(hmac_sha256(SECRET, f"{ts}.{body}"))`. En GET el body es `b""` y se firma `f"{ts}."`.

Metodos:

| Metodo | Descripcion |
| --- | --- |
| `publish(type_, data)` | Publica un evento individual |
| `publish_batch(events)` | Publica lote de eventos |
| `fetch_events(since, types, sources, limit, wait)` | Consume eventos con cursor |
| `poll_forever(handler, types, sources, interval, since, on_error, wait_seconds)` | Bucle de consumo con backoff exponencial |

## CI/CD y workflows

### `.github/workflows/agente.yml`

- Trigger: cron cada 30 min, `repository_dispatch` (tipo `vercel_deploy`), `workflow_dispatch` (modo `ciclo` or `informe` or `comando`).
- Concurrency: `group: agente`, `cancel-in-progress: false` (un agente a la vez).
- Resuelve `DATABASE_URL` con `NEON_API_KEY` via CLI de Neon.
- Ejecuta `node cli.js ciclo` or `informe` or `comando`.
- Publica resumen en GitHub Summary y opcionalmente en Discord via webhook.
- Dispara Neon Function `vantsbot` para entregar DMs del puente.

Secrets necesarios en el cuartel:

| Secret | Para que |
| --- | --- |
| `NEON_API_KEY` | Obligatorio. Resuelve `DATABASE_URL` |

### Como limitar el alcance de las pruebas

- Las pruebas del nucleo y del LLM usan implementaciones inyectadas (fetch falso, memoria RAM, fastify.inject). No tocan redes ni bases de datos reales.
- Las pruebas del sandbox ejecutan comandos reales en el entorno local (`echo`, `node -e`, `sleep`, `cat`). No escriben en disco ni hacen peticiones de red. Timeout corto (800 ms en test de timeout).
- Para ejecutar solo una suite: `node scripts/test_agente.js` desde `services/agent-service/`.
- Para ejecutar todas: el workflow `tests-agente.yml` las corre en secuencia.

## Limites, fallbacks y puntos no implementados

| Limite | Descripcion |
| --- | --- |
| Sandbox no aislada | La sandbox es validacion + auditoria, no aislamiento de proceso completo. Corre en el mismo runner/local |
| Sin `DATABASE_URL` | Memoria RAM: se pierde todo al reiniciar. No hay dedupe persistente entre ciclos |
| Sin `AGENT_LLM_KEY` | Modo reglas unicamente. NLU local entiende aproximadamente 15 patrones fijos en espanol |
| Sin `GITHUB_TOKEN` | Acciones automaticas quedan propuestas, nunca ejecutadas |
| Sin `VERCEL_TOKEN` | Chequeo `vercel_deploy` sale "omitido", accion `redeploy_vercel` queda propuesta |
| Max 2 redeploys Vercel por SHA | Guarda anti-bucle fija en `agent_events` |
| Max 5 pasos LLM | `MAX_PASOS = 5` en `llm.js`. Despues fuerza respuesta final sin tools |
| Max 256 KB por archivo sandbox | `agent_archivos` rechaza ficheros mayores |
| Max 32 KB salida sandbox | stdout+stderr recortados; se indica en la respuesta |
| Max 2000 caracteres mensaje chat | `endpoints/api.py` rechaza con 400 |
| Max 10 turnos historial chat | Servidor recorta a los ultimos 10 |
| VANTS-BUS en Vercel | No arranca como hilo daemon. Usar proceso independiente |
| Cursor del bus | Persiste en archivo local `.vants-cursor.json`. No garantiza entrega exactamente una vez si hay multiples consumidores |
| Healthz no prueba integraciones | `GET /healthz` solo verifica que el proceso responde. No ejecuta chequeos externos ni valida tokens de terceros |
