## Ejecutar el monitor

Necesitas Git y Node.js 20, la version utilizada en el workflow. No hay dependencias npm que instalar para este script.

```bash
git clone https://github.com/vantsgames/vants-proteger.git
cd vants-proteger
node monitor/monitor.js
```

<Warning>
  El comando consulta servicios externos reales. Revisa los destinos de `CHECKS` antes de ejecutarlo en otro entorno. Esta guia no representa una comprobacion actual de su disponibilidad.
</Warning>

## Comprobaciones

| Destino | URL | Marcador esperado |
| --- | --- | --- |
| Web | `https://vants.vants.workers.dev/` | `VANTS GAMES` |
| Bot Discord | `https://vantsbot.vants.workers.dev/salud` | `"ok":true` |

El script sigue redirecciones, comprueba un estado HTTP de 200 a 399 y busca los marcadores en los primeros 20 000 caracteres del cuerpo. Imprime el resultado, el estado HTTP y el tiempo de respuesta de cada consulta.

Si una comprobacion falla, finaliza con codigo `1`. Si todas pasan, finaliza normalmente. Los tiempos impresos son mediciones de esa ejecucion, no objetivos de rendimiento.

El marcador del bot solo comprueba la presencia del texto `"ok":true`. No interpreta el resto de su diagnostico ni garantiza que las tablas D1 o integraciones esten disponibles.

## Configuracion

Los destinos se definen en `CHECKS` y el tiempo limite en `TIMEOUT = 15000` dentro de `monitor/monitor.js`.

`monitor/config.example.json` contiene `webhookUrl`, `slowMs` y `timeoutMs`, pero el script no lee ese archivo. Modificarlo no cambia los destinos, no aplica un umbral de latencia ni activa notificaciones por webhook.

Para adaptar el monitor, cambia explicitamente las constantes del script y revisa el resultado antes de actualizar la programacion.

## GitHub Actions e incidentes

`.github/workflows/monitor.yml` define:

- Programacion `*/30 * * * *` y activacion manual mediante `workflow_dispatch`.
- Preparacion de Node.js 20 y ejecucion del monitor.
- Apertura o actualizacion de un issue con etiqueta `monitor-caida` si hay fallo.
- Comentario de recuperacion y cierre de los issues abiertos con esa etiqueta cuando vuelve a pasar.
- Permisos `contents: read` e `issues: write`.

La programacion declarada no demuestra que el workflow este habilitado o ejecutandose actualmente. Comprueba su historial en GitHub Actions para conocer resultados reales.

## Contrato de datos

El monitor no almacena datos persistentes. Solo emite logs de texto con estado, codigo HTTP y latencia. No recolecta informacion de usuarios, ni accede a bases de datos, ni modifica el estado de los servicios que consulta.

| Aspecto | Regla |
| --- | --- |
| Datos de entrada | Ninguno; solo constantes de URL y marcadores en codigo |
| Datos de salida | Logs de consola (estado, HTTP, ms, detalle de error) |
| Retencion | Ninguna; los logs viven solo en la ejecucion del workflow |
| Permisos del workflow | `contents: read`, `issues: write` |
| Etiqueta de incidente | `monitor-caida` con color `d73a4a` |

## Monitor, configuracion y CI para IA

El script esta disenado para ser ejecutado por un workflow de GitHub Actions, pero tambien puede correr localmente. No requiere variables de entorno ni archivos de configuracion externos.

### Puntos de edicion para un agente

Si un flujo de IA necesita adaptar este monitor, estos son los puntos exactos:

1. **`CHECKS` en `monitor/monitor.js`**: anade, elimina o modifica destinos. Cada entrada necesita `id`, `label`, `url` y opcionalmente `markers`.
2. **`TIMEOUT` en la linea 22 del script**: ajusta el tiempo limite en milisegundos.
3. **`.github/workflows/monitor.yml`**: modifica la expresion cron, el `timeout-minutes` del job (10 min por defecto) o los pasos de manejo de incidentes.

El archivo `monitor/config.example.json` es documentacion sin efecto en tiempo de ejecucion.

### Criterios de aceptacion del monitor

- Debe salir con codigo `0` cuando todos los checks respondan HTTP 200-399 y contengan sus marcadores.
- Debe salir con codigo `1` si al menos un check falla por estado HTTP, timeout o marcador ausente.
- El workflow debe abrir un issue nuevo con etiqueta `monitor-caida` si no existe ninguno abierto.
- Si ya existe un issue abierto con esa etiqueta, debe anadir un comentario con el log de la ejecucion fallida.
- Al recuperarse, debe comentar "Servicio recuperado" y cerrar todos los issues abiertos con `monitor-caida`.
- No debe requerir secretos adicionales ni tokens de terceros.

## Riesgos y limitaciones

| Riesgo | Impacto | Mitigacion observada |
| --- | --- | --- |
| Marcador fragil del bot | `"ok":true` como texto plano puede coincidir en otro contexto | El check limita la busqueda a los primeros 20 000 caracteres |
| Timeout fijo de 15 s | Falso negativo en condiciones de red degradadas | Editar `TIMEOUT` directamente en el script |
| Configuracion no funcional | `config.example.json` no se carga | Documentar que los cambios deben hacerse en el codigo fuente |
| README contradictorio | El texto incluye referencias a apps no presentes en el arbol | Esta guia se limita a los archivos verificados del commit `d879d6a` |
| Sin autenticacion en los checks | Solo valida disponibilidad publica | No pretende verificar funcionalidades protegidas por login |
| Posible falso positivo de recuperacion | Si un check es intermitente, el workflow puede abrir y cerrar issues repetidamente | No se observa deduplicacion ni ventana de estabilidad |
